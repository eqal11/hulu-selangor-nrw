# Hulu Selangor NRW Monitor

A static GIS dashboard demonstrating non-revenue water (NRW) monitoring for a water utility. It brings district metered area (DMA) water balances, infrastructure, leak reports and data quality checks into one browser view.

**All data is synthetic, for demonstration only.** This is a portfolio project, not an operational utility system.

## Problem and objectives

Water utilities need to identify areas with high losses, review leak reports and check asset data before planning interventions. Separate tables and maps make these tasks harder to compare.

- Compare monthly and annual NRW across DMAs.
- Relate water balances to pipes, meters, valves and leak locations.
- Identify records that need correction and export an issue list.
- Demonstrate reproducible data generation and transparent calculations.

## Features

- Leaflet map with OpenStreetMap and Esri World Imagery basemaps, four overlay layers, labels, popups and a visibility-aware legend.
- Annual and monthly reporting for January to December 2025, aggregate KPI cards and a linked DMA ranking.
- Selected DMA water balance bar, pipe length, average pipe age and unresolved leak count.
- QA/QC tab with five checks, filters by check and DMA, issue-to-map highlighting and filtered CSV export.
- Responsive desktop panel and collapsible mobile bottom sheet. Map bounds update after layout and tab changes.

## Data

All six files in `data/` are generated by [generate-data.js](generate-data.js). The default seed is `20251023`; the same seed produces the same output. The generator uses only Node.js built-in modules. It does not collect or download utility records.

Spatial files are GeoJSON FeatureCollections in WGS 84 / EPSG:4326, with `[longitude, latitude]` coordinates. Their fictional extent is approximately 101.59 to 101.69 longitude and 3.49 to 3.54 latitude around Hulu Selangor, Malaysia. Locality-inspired names do not identify actual DMA boundaries or utility assets.

| File | Included data with the default seed |
| --- | --- |
| `data/dma.geojson` | 8 fictional DMA polygons |
| `data/pipes.geojson` | 674 pipe segments, including 2 deliberately isolated segments |
| `data/assets.geojson` | 112 assets: 80 valves, 24 flow meters and 8 DMA inlet meters |
| `data/leaks.geojson` | 66 leak reports dated in 2025 |
| `data/water_balance.json` | 96 monthly records, 12 per DMA |
| `data/qa_injected_issues.json` | 20 deliberately injected pipe defects, affecting 2.9674% of pipe records |

The network consists of jittered grids. AC and pre-1995 pipes have higher leak probabilities by construction. Water balances are generated independently of individual leak reports. They are not a hydraulic simulation or a reconciliation of leak duration and loss volume.

## Method and calculation review

The generator constructs monthly balances in integer hundredths of a cubic metre before writing decimal values. The dashboard reads those values and aggregates them; it does not estimate production from the map or derive monthly real losses from leak reports.

### Water balance and NRW

Every generated monthly record satisfies:

```text
system_input_m3 = billed_authorised_m3 + unbilled_authorised_m3
                + apparent_losses_m3 + real_losses_m3
nrw_m3 = system_input_m3 - billed_authorised_m3
       = unbilled_authorised_m3 + apparent_losses_m3 + real_losses_m3
nrw_pct = round(100 * nrw_m3 / system_input_m3, 2)
```

For the selected period, the aggregate cards sum the relevant monthly volumes across all eight DMAs. Annual volumes sum all 12 months. Overall NRW uses volumes:

```text
overall NRW % = 100 * sum(nrw_m3) / sum(system_input_m3)
```

With the default data, annual input is **9,147,413.55 m³**, billed consumption is **5,852,841.51 m³**, NRW is **3,294,572.04 m³**, and overall NRW is **36.02%** when displayed.

### DMA percentages and the breakdown bar

A monthly DMA value uses the valid stored `nrw_pct`, falling back to NRW/input if that percentage is unavailable. Input must be positive. The annual choropleth, ranking, selected DMA heading and count of DMAs above 40% use the **arithmetic mean of the 12 monthly percentages**. The threshold is strictly greater than 40%. Map classes are below 30%, 30% to below 40%, 40% to below 50%, and 50% or above.

Each breakdown bar segment is `100 * component volume / selected DMA system input`. Annual bars use summed annual volumes. A bar is drawn only when all four component volumes are known, input is positive and their sum matches input within 0.02 m³.

**Calculation difference retained from the code:** annual DMA percentages are not annual volume ratios. For DMA-004, the displayed annual mean is **51.46%**, while annual NRW volume divided by annual input is **51.48%**. The overall KPI and breakdown bar use volume ratios. These definitions must not be presented as interchangeable; the application logic is unchanged.

### Leak and inventory measures

- Open leaks include `open` and `in_progress` reports whose report date falls within the selected month, or within 2025 for Annual. Estimated daily loss sums those reports' `est_loss_m3_day`. These are report cohorts using recorded statuses, not historical backlog snapshots or losses accumulated over the reporting period.
- Pipe length is `sum(length_m) / 1000` for records with the selected DMA ID. Invalid DMA references remain unassigned. Each segment is counted as a feature, even if its business ID is duplicated.
- Average pipe age is the mean of `2025 - install_year`, using only known integer years from 1 to 2025. Inventory measures do not change with the selected month.
- Annual balance calculations require 12 distinct monthly records per DMA; monthly calculations require one. Incomplete coverage or invalid required numeric values produce `n/a` rather than partial volume totals. Zero volumes and zero leak counts remain zero; percentages with zero input are `n/a`. Display formatting uses at most two decimal places.

## QA/QC checks

Checks run on all **852 infrastructure records**, independently of the period selector. DMA polygons provide reference boundaries; monthly water balances are not included in this QA denominator.

1. **Missing attributes:** null, absent or blank pipe material/installation year and asset condition.
2. **Duplicate IDs:** repeated pipe, asset or leak business IDs within their layer. Every member of a duplicate group is flagged.
3. **Orphan references:** nonexistent DMA IDs on pipes, assets or leaks; nonexistent pipe IDs on leaks. This checks existence, not unique resolution of duplicate IDs.
4. **Disconnected pipes:** a start or end endpoint has no other pipe endpoint or asset within 1 m. A spatial grid selects candidates before a haversine distance check. Both endpoints of the same pipe are excluded as neighbours. This is a proximity check, not a test of hydraulic reachability.
5. **Outside boundary:** a pipe's half-length midpoint or leak point lies outside its assigned DMA. Polygon holes are supported and boundary points count as inside. Unknown DMA references are handled as orphans. Invalid pipe/leak geometry is reported as an untestable boundary check; invalid geometry is skipped for map drawing and endpoint indexing.

```text
pass rate % = 100 * (records checked - unique affected records) / records checked
detection rate % = 100 * matched injected defects / logged injected defects
```

Detection requires a matching layer, feature locator and defect type. The optional card is hidden when the log is unavailable or invalid; a zero denominator produces `n/a`.

The default fixture returns **23 issues**: 12 missing attributes, 6 duplicate-ID records, 3 orphan references, 2 disconnected segments and 0 outside-boundary issues. There are 23 unique affected records, giving a **97.3%** pass rate. All **20/20 injected defects** are matched. The three additional duplicate donors explain why issue rows exceed injection records. **100% detection verifies these synthetic test cases; it does not establish accuracy on real utility data.**

## Tech stack

- HTML, CSS and plain JavaScript for the interface and calculations.
- Leaflet 1.9.4 for mapping, loaded from a pinned CDN URL.
- GeoJSON and JSON loaded with relative `fetch()` requests.
- Node.js built-in modules for reproducible synthetic data generation.
- OpenStreetMap and Esri World Imagery tile services. Their attributions remain visible on the map.

There is no framework, backend, database or build step. The generator can run offline; the dashboard needs internet access for Leaflet and basemap tiles.

## Run locally

Use Node.js 18 or later. The server example also requires Python 3. From the project folder containing `index.html`:

```sh
node generate-data.js
python -m http.server 8000 --bind 127.0.0.1
```

Open [http://127.0.0.1:8000/](http://127.0.0.1:8000/). On systems where Python is named `python3` or `py`, substitute that command. Any static HTTP server can be used instead. Opening `index.html` directly with `file://` will not load the JSON files reliably.

Generation is optional when using the included dataset. Running it overwrites the six same-named files in `data/`. An alternate seed/output directory is supported:

```sh
node generate-data.js --seed 12345 --out-dir ./data-alternate
node --check app.js
```

The dashboard always reads `./data/`; generating an alternate directory alone does not switch its inputs.

## Limitations

- Synthetic geography, balances and leak probabilities do not represent measured utility performance. No savings, response-time improvements or field accuracy have been established.
- Annual DMA means and annual volume ratios use different aggregation methods, as documented above.
- No repair timestamps, historic status transitions, meter uncertainty or billing-period reconciliation are modelled.
- Missing dates, missing business IDs and arbitrary attribute validity are not comprehensively audited. The five checks have a defined scope and do not constitute a full GIS validation suite.
- An endpoint proximity failure may be a valid dead end in a real network. A midpoint test can miss a pipe that crosses a boundary elsewhere.
- No authentication, editing, persistent issue resolution or live data ingestion. Period options and pipe-age reference year are fixed to 2025.
- Large utility datasets would require performance testing and a different data-loading strategy.
